# MatchMark v2 Spec

Scoring for WA1500/PPC competitions at a single club. Vocabulary is in `GLOSSARY.md`; decisions are in `docs/adr/`.

## Scope

In: competitions, a persistent shooter registry, lane-paired scoring devices, live spectator view, results report (`.xlsx`), internal detailed CSV, admin database backup.

Out for v1: classification and ranking, relays, Rifle, 60/48 beyond course data, offline operation, PDF/JSON export, multi-club hosting, accounts for scorers.

Future: relays; Rifle; DNS-01 and other ACME challenge methods; CDN-hosted frontend; multi-club tenancy; offline queue; classification.

## Users and flow

- Admin (named user with username and password, 12-hour cookie session; the first admin is seeded from `ADMIN_USERNAME` and `ADMIN_PASSWORD` when there are no users): creates a competition, picks the course of fire, adds entries from the shooter registry (or creates new shooters), assigns lanes and categories, opens pairing, sets spectator visibility, watches progress, unlocks and corrects stages, finishes the competition, downloads the results report. A user changes their own password at `/admin/password` by supplying the current one (new password 16-128 characters); this ends their other sessions. A user whose password was reset (temporary password) is flagged and can reach only change-password and logout (other endpoints answer 403 `password_change_required`) until it is changed. Admins manage users at `/admin/users` (API `GET`/`POST /api/users`, admin only; regular users get 403): create a user with a username, a role (`admin` or `user`) and a temporary password (16-128 characters) that the user must change at first login, and list users with role and status. Per user: `POST /api/users/{userID}/deactivate` and `/reactivate` (a deactivated user cannot log in and their sessions end at once), `POST /api/users/{userID}/reset-password` (temporary password, forces a change at next login, ends sessions) and `PUT /api/users/{userID}/role` (promote or demote; demotion ends sessions and clears the backup permission) and `PUT /api/users/{userID}/backup-permission` (`{"can_download_backup": bool}`; admins only, a regular user answers 422). The seeded admin has the backup permission; `GET /api/admin/backup` answers 403 `backup_not_permitted` to users and admins without it, and the UI hides the Backup link. The last active admin cannot be demoted or deactivated (409); unknown users answer 404. Users are never deleted. Usernames are 3-32 characters from `a-z`, `0-9`, `.`, `_`, `-`, stored lowercase, unique case-insensitively and never reused; a taken name answers 409. Regular users cannot manage users or take a backup but can use every competition, shooter and entry feature. `GET /api/admin/session` returns the signed-in `username`, `role` and `can_download_backup`.
- Scorer (device): opens a pairing link once, then sees only "Scoring lane N: name", enters ring counts for the current stage and locks it.
- Spectator (no login): live standings and per-stage progress, subject to admin's per-competition field visibility.

## Scoring rules

- Score lane is the next manned lane after the scorer's own lane, wrapping, derived server-side from the device's pairing and current entries. A paired lane is always manned.
- A competition with one manned lane requires admin scoring.
- Everyone shoots in step. Entries change only between stages. A withdrawn entry is flagged and keeps its results; later stages re-target to the next manned lane.
- Hits per stage are seven counts (X, 10, 9, 8, 7, 0, miss) that must sum to the stage's expected shots. X scores 10. 0 and miss score 0.
- Lock stores the scorer's lane and name. Only the admin can unlock and edit; an admin edit of a locked stage keeps it locked.
- The admin entries list shows each stage's score and shots entered, for open as well as locked stages. An open stage with all expected shots entered is shown as "Scored, not locked".
- Course data and shot counts live in one `rulebook` package and match rulebook Issue 2026-01-01 §7. The 150 course is 10 stages grouped as Match 1 (7 yd, 15 yd), Match 2 (25 yd), Match 3 (50 yd), Match 4 (2 × 25 yd), Match 5 (7 yd, 25 yd, 50 yd, 25 yd × 6).

## Competition model

- Competition: name, date, course of fire (150 default; 60 and 48/40 selectable; no partial courses), status draft/active/finished, spectator visibility flags. A draft competition can be edited from its page (name, date and course); the course is locked once it has entries, and an active or finished competition cannot be edited.
- Shooter: last name, first name, sex, country, club, optional WAID. Persistent. A shooter without a WAID is a new shooter.
- Entry: shooter, category (Revolver, Pistol, Revolver OS, Pistol OS, Rifle), lane, withdrawn flag.
- Stage per entry, created when the entry is added: expected shots, seven ring counts, locked state, scorer.
- Device pairing: token, competition, lane, revoked flag.

## Results report

Filled in from the embedded `Results reporting mal.xlsx` using `excelize`. One sheet per category; competition name and date in the header; known shooters as WAID + total result, extra rows inserted as needed; new shooters in the "New shooters" block with last name, first name, sex, country, club, result. The template is a replaceable embedded file.

An internal detailed CSV lists ring counts per stage per entry for the club's own records. The CSV starts with a UTF-8 byte-order mark so spreadsheet applications show non-ASCII names correctly. Both downloads are named `<competition name>-<competition date>.<ext>` (for example `Test2-2026-10-20.xlsx`): characters other than letters, digits and `_` collapse to a single `-`, names are capped at 60 characters, an empty name becomes `results`, and non-ASCII letters are sent via an RFC 5987 `filename*`.

## API and frontend

JSON REST API under `/api`, documented with OpenAPI; admin and spectator endpoints separated; spectator endpoints are unauthenticated. Spectator, admin and scorer screens receive live updates over server-sent events (one stream per role and competition, see ADR 0010) instead of polling. Frontend is a Svelte + Vite + TypeScript SPA with a typed client generated from the OpenAPI spec, no service worker or IndexedDB. All strings in English.

`GET /api/rulebook` is read-only and unauthenticated. It returns the courses keyed `150`, `60`, `48` and `40` (label, discipline, total shots, stages with distance, expected shots, time and position), the weapon classes per discipline and the ring values. `internal/rulebook` is its only source, including the course labels; the SPA course dropdowns read from it.

## Backend

Go, chi, SQLite-format storage via Turso Database and `turso.tech/database/tursogo` (`CGO_ENABLED=0`, native library loaded at runtime; see ADR 0005), embedded ordered migrations, strict handler → service → repository layering, `excelize` for xlsx, `certmagic` for ACME. Passwords hashed with argon2id (random salt per user, PHC string, m=19456 KiB, t=2, p=1, rehashed at login when weaker, constant-time comparison, dummy verification for unknown usernames; login answers wrong password and unknown username identically; failed logins are limited per IP and delayed per username, never hard-locked); session cookie `HttpOnly`, `SameSite=Lax`, `Secure` when `BASE_URL` is https.

## Configuration (environment only)

`ADMIN_USERNAME` and `ADMIN_PASSWORD` (16-128 chars), both required only while there are no users, `DB_PATH`, `LISTEN_ADDR`, `BASE_URL`, `TRUSTED_PROXY`, `TLS_CERT_FILE`, `TLS_KEY_FILE`, `ACME_DOMAIN`, `ACME_EMAIL`, `TURSO_GO_CACHE_DIR` (writable path for the extracted native library), `REPLICATION_URL` (empty disables Replication), `REPLICATION_INTERVAL` (default 60s).

## Replication

Optional and off by default. When `REPLICATION_URL` is set, the primary opens its database through the tursogo sync API and pushes to a self-hosted `tursodb --sync-server` on another host, every `REPLICATION_INTERVAL` and when a competition finishes. Push-only: the replica is never merged back. Failures are logged and retried and never block scoring. The sync server has no authentication, so it must only be reachable over a private network; across the public internet use snapshot files instead. Restore is copying the replica's database file to a new primary. See ADR 0005.

TLS modes: plain HTTP (default, behind a proxy); static certificate; ACME via certmagic with certificates stored in the data volume.

## Score log

Whenever a device or a user locks a stage, the server writes one JSON `info` line to stdout with `msg` and `event` `stage_locked`. Unlocking a stage writes a line with `event` `stage_unlocked` and the same fields. A user's overwrite of ring counts on a locked stage keeps it locked and takes it over: it writes a new `stage_locked` line with the new counts, `locked_by` and `scorer_name` set to the user's username, and the database records the same, so the original device lock is no longer visible; `locked_at` keeps the original lock time. The `stage_unlocked` line carries the `locked_by`, `scorer_name` and `locked_at` the stage had just before it was unlocked. Fields: `schema_version` (1), `event`, `emitted_at` (UTC, fixed-width millisecond precision such as `2026-10-19T16:45:14.123Z`), `seq` (integer that strictly increases for every line within a server process, assigned under a mutex so it matches write order), `competition` {`id`, `name`, `date`, `course_of_fire` {`key`, `discipline`, `total_shots`}}, `entry` {`id`, `lane`, `category`, `shooter` {`waid`, `first_name`, `last_name`, `club`}}, `stage` {`number`, `expected_shots`}, `ring_counts` (X, 10, 9, 8, 7, 0, miss), `locked_by` (lane number for a device lock, username for a user lock), `scorer_name` (the username for a user lock), `locked_at`. The line is written after the database write succeeds; a log failure never fails the lock. Editing a competition, an entry or a shooter re-emits `stage_locked` for every affected locked stage (a shooter edit covers all of that shooter's entries across competitions) with the `locked_by`, `scorer_name` and `locked_at` as currently recorded and a new `emitted_at` and `seq`; unlocked stages emit nothing. Replay: the last line per competition, entry and stage by (`emitted_at`, `seq`) wins; `seq` restarts at 1 after a server restart, which is safe because `emitted_at` is compared first, and a final `stage_unlocked` means the stage is not scored. Entries with no locked stage are not recoverable, and lines contain personal data. The `restore` subcommand (`matchmark restore [file]`, stdin when no file is given; no `ADMIN_USERNAME` or `ADMIN_PASSWORD` needed) parses the log, skips non-score and malformed lines (including an unknown course key, a `locked_by` that is neither a positive lane number nor a non-empty username, or an `emitted_at` not in the fixed-width layout) with a count, rejects an unknown `schema_version`, applies the replay rule with context taken from the latest line, and prints a summary of the competitions, entries and scored stages. Without `--apply` it is a dry run and writes nothing. With `--apply` it opens the database from the server configuration (`DB_PATH`), runs migrations and recreates each competition (status `finished`), its shooters (matched by WAID, else by name and club), entries and scored stages with ring counts, lock state, `scorer_lane` (NULL for a user lock), `scorer_name` and `locked_at`, keeping the original competition and entry ids. It refuses a database that already contains competitions or shooters and changes nothing; all competitions are written in one transaction, so a failure changes nothing; flags may follow the file path; `--merge` instead applies only data whose ids match or are new, lists conflicts (a differing competition, entry, or locked stage counts, `locked_by`, `scorer_name` or `locked_at`) and never overwrites them. It is idempotent by ids and leaves already locked stages untouched. Sex and country are not in the log, so restored shooters get sex `M` and an empty country. Unscored entries, devices and pairings are not restored and the command says so. See ADR 0007.

## Audit log

Every mutation, login, failed login, failed password change, report download, backup download and `reset-password` run is written to the `audit_log` table (migration 014) and, after the database write succeeds, to stdout as a JSON `info` line with `msg` `audit`. The service layer writes both, so every entry point is covered; a write failure is logged and never fails the request. Fields: `time` (UTC), `user_id` (absent for devices and failed logins), `username` (the username at the time of the event; the attempted username for a failed login; `device` for a paired device), `action`, `target`, `details`, `ip` (the client IP, honouring `TRUSTED_PROXY`). Actions: `competition.create|update|status|visibility|delete`, `shooter.create|update|delete`, `entry.add|update|withdraw|delete`, `stage.set_counts|lock|unlock`, `device.pair|revoke`, `user.create|deactivate|reactivate|reset_password|set_role|set_backup_permission|change_password|change_password_failed`, `login`, `login_failed` (details `throttled` when the per-IP limit answered), `report.download` (details `xlsx` or `csv`) and `backup.download`. Counts entered and locks made by a paired device have actor `device` and details `lane <n> competition <id>`; `user.reset_password` from the `matchmark reset-password` command has actor `cli`. A failed password change (wrong current password) is recorded as `user.change_password_failed`. Only successful changes are recorded. Targets look like `competition:3`, `competition:3/entry:7/stage:1` or `user:2`. Entries are kept forever; database triggers reject updates and deletes and there is no write or delete endpoint. `GET /api/audit-log` (admin only; users get 403) returns `{entries, total, page, page_size}` newest first, filtered by `user` (case-insensitive username), `action` (exact), `from` and `to` (`YYYY-MM-DD`, UTC, inclusive), with `page` and `page_size` (default 50, maximum 200); invalid parameters answer 422. The admin UI shows it at `/admin/audit` (link visible to admins only). Seeding the first admin is not audited. See ADR 0011.

## Delivery

Repository root: `Dockerfile`, `docker-compose.yml` (app plus `./data` volume only), `docs/`, `GLOSSARY.md`, `README.md`, `AGENTS.md`. Code in `source/` (Go module root; `source/web/` for the SPA). Dockerfile: Alpine Node stage builds `web/`, Alpine Go stage embeds `web/dist` and builds with `CGO_ENABLED=0 -tags musl`, final Alpine 3.24 image (the tursogo native library needs a libc to `dlopen`) running non-root with `TURSO_GO_CACHE_DIR` on a writable path. Supported targets: linux/amd64 and linux/arm64 (64-bit Pi OS only) as image and binary; darwin/amd64, darwin/arm64 and windows/amd64 as unsigned release binaries (ADR 0012). The admin UI offers a database backup download; it uses `VACUUM INTO` with a string literal path, which Turso Database supports (bound parameters are rejected).

CI (GitHub Actions) builds, tests and smoke-tests the image natively: `ubuntu-latest` for amd64, `ubuntu-24.04-arm` for arm64, no QEMU, plus a build-only `macos-latest` job. The smoke test opens a database inside each image because a library-loading failure only shows at runtime.
