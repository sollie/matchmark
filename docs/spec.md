# MatchMark v2 Spec

Scoring for WA1500/PPC competitions at a single club. Vocabulary is in `GLOSSARY.md`; decisions are in `docs/adr/`.

## Scope

In: competitions, a persistent shooter registry, lane-paired scoring devices, live spectator view, results report (`.xlsx`), internal detailed CSV, admin database backup.

Out for v1: classification and ranking, relays, 60/48 beyond course data, offline operation, PDF/JSON export, multi-club hosting, accounts for scorers.

Future: relays; DNS-01 and other ACME challenge methods; CDN-hosted frontend; multi-club tenancy; offline queue; classification.

## Users and flow

- Admin (named user with username and password, 12-hour cookie session; the first admin is seeded from `ADMIN_USERNAME` and `ADMIN_PASSWORD` when there are no users): creates a competition, picks the course of fire, adds entries from the shooter registry (or creates new shooters), assigns lanes and categories, opens pairing, sets spectator visibility, watches progress in the control room, starts each next stage, accepts on a shooter's behalf, unlocks and corrects stages, finishes the competition, downloads the results report and detailed CSV from the competition list (buttons shown only for finished competitions). A user changes their own password at `/admin/password` by supplying the current one (new password 16-128 characters); this ends their other sessions. A user whose password was reset (temporary password) is flagged and can reach only change-password and logout (other endpoints answer 403 `password_change_required`) until it is changed. Admins manage users at `/admin/users` (API `GET`/`POST /api/users`, admin only; regular users get 403): create a user with a username, a role (`admin` or `user`) and a temporary password (16-128 characters) that the user must change at first login, and list users with role and status. Per user: `POST /api/users/{userID}/deactivate` and `/reactivate` (a deactivated user cannot log in and their sessions end at once), `POST /api/users/{userID}/reset-password` (temporary password, forces a change at next login, ends sessions) and `PUT /api/users/{userID}/role` (promote or demote; demotion ends sessions and clears the backup permission) and `PUT /api/users/{userID}/backup-permission` (`{"can_download_backup": bool}`; admins only, a regular user answers 422). The seeded admin has the backup permission; `GET /api/admin/backup` answers 403 `backup_not_permitted` to users and admins without it, and the UI hides the Backup link. The last active admin cannot be demoted or deactivated (409); unknown users answer 404. Users are never deleted. Usernames are 3-32 characters from `a-z`, `0-9`, `.`, `_`, `-`, stored lowercase, unique case-insensitively and never reused; a taken name answers 409. Regular users cannot manage users or take a backup but can use every competition, shooter and entry feature. `GET /api/admin/session` returns the signed-in `username`, `role` and `can_download_backup`.
- Scorer (device): opens a pairing link once, then sees only "Scoring lane N: name", enters ring counts for the current stage and locks it, then waits (Lock stage stays disabled while the entered ring counts differ from the saved ones or no valid counts are saved, and a status line says "Unsaved changes: press Save, then Lock stage." or "Saved ✓"); as a shooter the device also accepts or disputes its own result, and after a dispute the scorer re-scores the stage.
- Spectator (no login): live standings under one slim status row that wraps on small screens (competition picker, competition status, `Stage N of M` from the snapshot's `current_stage` and `total_stages`, the snapshot's `status` keeping the competition status (and the finished links) current without reloading the list, the course's stage count from the rulebook, an `x/y accepted` count for the current stage that excludes withdrawn entries, and the Live or Offline badge with the last update time; a finished competition shows `Finished` instead of the stage position and count; there are no progress bars and no separate progress endpoint), with each shooter's stage state (`not_started`, `in_progress`, `awaiting_acceptance`, `accepted`; a disputed stage reopens as `in_progress`, and only an accepted stage shows its score), always visible and shown as a coloured cell with a title, an accessible label and a legend; the score itself follows the stage-scores visibility flag, other fields follow admin's per-competition field visibility.
- Results view (no login): `/results` picks among finished competitions (newest first) and `/results/{id}` is the deep link; the spectator page links to it once the competition is finished. A printable sheet (print stylesheet hides the site chrome) shows the club logo and name, competition name, date and course, then per category a table of rank, shooter, WAID, each stage's score, total and X count, ranked by total then X count (rank shared only when both are equal; withdrawn entries excluded), and a New shooters list (shooters without a WAID). It carries no classification or medals and honours the visibility flags: hidden names also hide WAID and the new shooters list, hidden stage scores omit the stage columns, hidden ring counts omit X. `GET /api/spectator/competitions/{id}/results` returns `{competition{id,name,date,course,course_label}, stages[], categories[{category, rows[{rank, last_name?, first_name?, waid?, club?, country?, stages[{stage, score?}], total, x_count?}]}], new_shooters[{last_name, first_name, category, club?, country?, total, x_count?}]}` and answers 404 unless the competition is finished.

## Club settings

One row in `club_settings` (migration 019): the club `name`, the `logo` BLOB with its `logo_content_type`, and a `version` that increases on every edit. Admins edit it at `/admin/club`. `GET /api/club` is public and returns `{name, has_logo, version}` (name empty when unset). `PUT /api/club` (admin only) takes `{name}`, trims it and accepts at most 100 characters. `PUT /api/club/logo` (admin only) takes the raw image as the request body with `Content-Type` `image/png` or `image/jpeg`; SVG and every other type, an empty body, a body over 512 KB, a body whose bytes do not match the declared type and an image over 2048 by 2048 pixels answer 422. `DELETE /api/club/logo` (admin only) removes it. `GET /api/club/logo` is public, answers 404 without a logo and sends `Cache-Control: no-cache`; clients append `?v=<version>` as a cache-buster, which the server ignores. The settings live in the database, so Backup and Replication cover them. Changes are written to the Audit log (`club.update`, `club.logo.set`, `club.logo.delete`). Regular users get 403 on every write.

## Results PDF

`GET /api/competitions/{id}/results` renders the Results view as a PDF on demand (ADRs 0015 and 0016). It is public, honours the visibility flags like the Results view and answers 404 unless the competition is finished. `GET /api/admin/competitions/{id}/results` needs an admin session, shows every column whatever the flags and is audited as a `report.download` with details `pdf`. `format` defaults to `pdf`; any other value answers 422. The document is A4 portrait with one page per category (long categories continue on further pages) and a final page for new shooters. Every page repeats a header with the club logo and name, the competition name, date and course, and a footer with the generation time. Responses are `application/pdf` with `Cache-Control: private, no-cache` and `Content-Disposition: attachment; filename="<competition name>-<competition date>-results.pdf"`; nothing is stored. Both endpoints sit behind the render guard; the admin one is not coalesced, so every request renders and is audited. The Results view has a Download PDF button and the admin competition list has a PDF button beside XLSX and CSV for finished competitions.

## Scorecard copy

`GET /api/scorer/scorecard/{competitionID}/{lane}` renders the Scorecard of the entry on that lane as a PNG on demand (ADRs 0015 and 0016). It is public, outside the device middleware and ignores the spectator visibility flags. `format` defaults to `png`; any other value answers 422. It answers 404 for an unknown or unfinished competition, an empty lane and a withdrawn entry. The card shows the shooter, WAID when known, category, lane, competition name and date, the club logo and name (from Club settings), one row per stage of the course of fire with distance, shot count, ring counts X, 10, 9, 8, 7, 0 and M, the stage score and the scorer (the range admin for admin-scored stages), and totals. Rows and shot counts come from `internal/rulebook`; only accepted stages are filled in and counted, others stay blank. The response is `image/png` with `Cache-Control: private, no-cache`; nothing is stored. The SPA route `/scorecard/{competitionId}/{lane}` is public and shows the shooter and the scorer of each accepted stage as text (from the summary endpoint below), the PNG (image URL with a `v` cache-buster, alt text naming the shooter and lane) with a prominent Download PNG link (`download=1`), or a clear message when the card is not available (404); on `429` or `503` (render limits) it asks to try again shortly and retries after the `Retry-After` delay, and an image that fails to load gets the same treatment or a retry button; the spectator standings link to it per lane once the competition is finished. `download=1` adds `Content-Disposition: attachment` with `<competition name>-<competition date>-lane-<n>.png` (same name rules as the report downloads).

`GET /api/scorer/scorecard/{competitionID}/{lane}/summary` returns `{shooter, lane, scorers: [{stage, scorer}]}` as JSON, one item per accepted stage (`Range admin` for admin-scored stages). It has the same availability as the card (404 unless the competition is finished and the lane has a kept entry), is public and ignores the visibility flags; the SPA uses it so the names are text rather than only pixels.

The endpoints run behind the render guard (`handler.RenderGuard`, ADR 0016): at most 4 renders at once with a short queue (`503` with `Retry-After` when full), identical public requests share one render (admin PDF requests do not, so each is audited), and each client IP may make 20 requests per minute per resource (`429` with `Retry-After`). The client IP honours `TRUSTED_PROXY`. Edge rate limiting is left to the CDN.

## Scoring rules

- Score lane is the next manned lane after the scorer's own lane, wrapping, derived server-side from the device's pairing and current entries. A paired lane is always manned.
- A competition with one manned lane requires admin scoring.
- Everyone shoots in step on the competition's current stage (`competitions.current_stage`, migration 017). Activation starts at stage 1. `POST /api/competitions/{id}/next-stage` (admin) moves the pointer by one and answers 409 until every manned, non-withdrawn lane has accepted the current stage, and when the competition is not active or is on its last stage. Devices can score, lock, accept and dispute only the current stage (409 otherwise); the admin can still edit, lock, accept and unlock any stage, and an admin unlock after the pointer moved on reopens that stage without moving the pointer. The last acceptance of the last stage (by a device or the admin) finishes the competition through the normal finish path (pairings revoked, replication push, audit). Unlocking a stage of a finished competition leaves it finished. Entries can be added and moved to another lane only while the competition is a draft (an active competition still allows changing an entry's category; a finished one allows nothing). Withdrawing is allowed in a draft or at the gate (current stage fully accepted, before the next stage starts) and never once finished; a withdrawn entry is flagged and keeps its results, and later stages re-target to the next manned lane. Competitions keep independent pointers.
- Hits per stage are seven counts (X, 10, 9, 8, 7, 0, miss) that must sum to the stage's expected shots. X scores 10. 0 and miss score 0.
- A stage is `open`, `awaiting_acceptance` or `accepted`. A device lock leaves the stage awaiting acceptance with its hits frozen and records the scorer's lane and name. An admin lock (as the signed-in user) or an admin accept (`POST .../stages/{stage}/accept`, only from awaiting acceptance, else 409) makes it accepted. Only the admin can unlock (back to open, hits kept) and edit; an admin edit of an awaiting or accepted stage ends accepted and takes the stage over. Standings, the results report and the CSV count only accepted stages; the admin entries list shows every stage's score and status. The shooter accepts or disputes from their own device: `POST /api/scorer/stages/{stage}/accept` and `.../dispute` act only on the stage of the device's own lane, answer 409 unless it is awaiting acceptance and 403 for a stage the device itself locked. A dispute reopens the stage as `open` with hits kept and sets `disputed_at`, which the next lock clears; accept records the lane as `accepted_by`. The scorer snapshot carries a server-derived `phase`: `scoring` while the current stage of the device's score lane is open, `next_stage` when the admin has started the stage (`stages.started`, migration 018) and the scorer has not yet saved hits or locked it, so a re-pair or restore never shows it (the device shows a banner and a Continue button), `not_started` while the competition is a draft (the device can be paired before the start and shows a waiting screen with only its lane, no shooter name; the stream switches it to scoring on activation; writes answer 409), `finished` once the competition is finished (the pairing is revoked but the session still answers with only `lane` and `phase`, and an open stream ends with a final `finished` snapshot, so the device forgets its token at once and navigates to its own lane's scorecard page (`competition_id` and `lane` are in every session); a stream request with the token of a finished competition answers 410, which the client treats as terminal; writes answer 409). The client resets its reconnect backoff only after a stream has stayed open for several seconds, so a connection that closes at once keeps backing off, otherwise `waiting`, or `needs_acceptance` with an `acceptance` object (stage, ring counts, total, scorer name) when the device's own stage awaits acceptance, so a shooter who also scores sees the request only after locking their own scoring. Each snapshot stage carries its ring counts and a `disputed` flag, so the Disputed notice and the prefilled values survive a reload. The device shows a waiting screen with a banner and a Review result button, a read-only result (total, X count, stage chip, per-ring bars) with Accept and Dispute, where Dispute asks for a one-tap confirmation (Confirm dispute or Cancel) before anything is sent, and the Disputed notice; banners only, no push, sound or vibration. Accept and dispute are written to Stage events, the Score log and the Audit log (`stage.accept`, `stage.dispute`). The session and the competition JSON carry `current_stage`; an active competition's admin page shows the control room (below).
- Dispute history: `GET /api/competitions/{id}/stage-events` (admin; 404 for an unknown competition, 422 for a bad `stage`) returns `{events, scorers}`. `events` are the Stage events oldest first (`id`, `time`, `stage`, `entry_id`, `event` of `locked`, `accepted`, `disputed`, `accepted_all` or `unlocked`, `actor_type` `device` or `user`, `actor_name`, `shooter_name`, `scorer_name`). Device events carry the shooter and scorer resolved from the pairing when they happened. The optional exact filters `scorer`, `shooter` and `stage` narrow the events, and `scorers` holds `locks` and `disputes` per scorer name over the filtered events (admin lock and accept events carry no scorer, so the admin is never counted) so a scorer who is corrected on every stage stands out. The admin page shows it as the Dispute history section with scorer, shooter and stage filters, for every competition that is not a draft.
- Control room: `GET /api/competitions/{id}/control-room` (admin; 409 for a draft) returns `current_stage`, `can_start_next`, `can_accept_all` and one row per manned, non-withdrawn lane with `lane`, `entry_id`, `shooter_name`, `scorer_name` (the locking scorer, else the derived scorer, empty when the lane is admin-scored), `status`, `disputed`, `disputes` (disputes across all stages), `paired` and `connected`. `connected` is best-effort: it is true while the lane's device holds an open scorer stream, is kept in memory only, never stored, and is labelled best-effort in the UI. `can_start_next` is true at the gate; `can_accept_all` is true when no manned lane is open and at least one awaits acceptance. `POST /api/competitions/{id}/accept-all` (admin) accepts every awaiting stage of the current stage in one transaction (stage events `accepted_all`, audit `competition.accept_all`, auto-finish on the last stage) and answers `{accepted}`; it answers 409 while any manned lane is open or the competition is not active. The grid updates live from the admin stream, including when a device connects or disconnects. The page offers Start next stage and Accept all (each disabled unless allowed) and per-row Accept and Unlock, which work for lanes without a paired device; an admin lock of such a lane is final.
- The admin entries list shows each stage's score and shots entered, for open as well as awaiting-acceptance and accepted stages. An open stage with all expected shots entered is shown as "Scored, not locked".
- Course data and shot counts live in one `rulebook` package and match rulebook Issue 2026-01-01 §7. The 150 course is 10 stages grouped as Match 1 (7 yd, 15 yd), Match 2 (25 yd), Match 3 (50 yd), Match 4 (2 × 25 yd), Match 5 (7 yd, 25 yd, 50 yd, 25 yd × 6).

## Competition model

- Competition: name, date, course of fire (150 default; 60 and 48/40 selectable; no partial courses), status draft/active/finished, spectator visibility flags. A draft competition can be edited from its page (name, date and course); the course is locked once it has entries, and an active or finished competition cannot be edited.
- Shooter: last name, first name, sex, country, club, optional WAID. Persistent. Names are stored as a Normalized name: last name uppercase, first name with each word capitalised (also after a hyphen or apostrophe), whitespace trimmed and collapsed, Unicode-aware (`service.NormalizeLastName` and `service.NormalizeFirstName`). `POST /api/shooters` and `PUT /api/shooters/{id}` answer 422 for a name that is not already normalized; `POST /api/shooters/import` normalizes the WA1500 names before matching and saving. Migration 020 normalizes every stored shooter name once at startup (the rule lives in `internal/names`); shooters whose name then equals another shooter's name are never merged and are logged as a `shooter name collision after normalization` warning with `last_name`, `first_name` and `shooter_ids` for admin follow-up. A shooter without a WAID is a new shooter. `GET /api/shooters` takes optional `q` (case-insensitive partial match on WAID or on first and last name in either order; `%` and `_` are literal) and `limit` (1-100; 422 otherwise; defaults to 20 when `q` is given, otherwise all shooters). The entry form picks the shooter through a search combobox (Shooter) that queries the registry after a short debounce, lists name, WAID, club and country, supports arrow keys, Enter and Escape, hides shooters already entered and shows "No match" when nothing is found.
- Entry: shooter, category (Revolver, Pistol, Revolver OS, Pistol OS, Carbine), lane, withdrawn flag. `internal/rulebook` defines the categories each course allows: 150 shots Revolver, Pistol, Revolver OS, Pistol OS and Carbine (shot on reduced WA1500-29 targets; scoring is unchanged); 60 shots Revolver, Pistol, Revolver OS and Pistol OS; 48 shots Revolver and Pistol; 40 shots Revolver only; Carbine only on 150. Carbine entries share the competition and lane rotation with the other categories. `GET /api/rulebook` carries them as `courses[].categories` (string array). Creating or updating an entry with a category the course does not allow answers 422; existing entries are not migrated. The add-entry and edit-entry Category dropdowns list only the categories of the competition's course; the add form falls back to the first allowed category when the selection is not allowed.
- Stage per entry, created when the entry is added: expected shots, seven ring counts, status (`open`, `awaiting_acceptance`, `accepted`), `accepted_by`, `accepted_at`, `disputed_at`, scorer. Every status change is also appended to `stage_events` (migration 016: event, actor type and name, scorer, shooter, time).
- Device pairing: token, competition, lane, revoked flag.

## Results report

Filled in from the embedded template (`docs/references/results_reporting_template.xlsx`) using `excelize`. One sheet per category; competition name and date in the header; known shooters as WAID + total result, extra rows inserted as needed; new shooters in the "New shooters" block with last name, first name, sex, country, club, result. The template is a replaceable embedded file.

The `.xlsx` report and the detailed CSV are downloaded with buttons in the admin competition list, shown only for finished competitions; the endpoints themselves do not check the status.

An internal detailed CSV lists ring counts per stage per entry for the club's own records; only accepted stages are counted (others appear with zero counts and `accepted` false) and the same holds for the `.xlsx` report. The CSV starts with a UTF-8 byte-order mark so spreadsheet applications show non-ASCII names correctly. Both downloads are named `<competition name>-<competition date>.<ext>` (for example `Test2-2026-10-20.xlsx`): characters other than letters, digits and `_` collapse to a single `-`, names are capped at 60 characters, an empty name becomes `results`, and non-ASCII letters are sent via an RFC 5987 `filename*`.

## API and frontend

JSON REST API under `/api`, documented with OpenAPI; admin and spectator endpoints separated; spectator endpoints are unauthenticated. The spectator snapshot carries `current_stage`, and each standing's stage entry carries `state`. Spectator, admin and scorer screens receive live updates over server-sent events (one stream per role and competition, see ADR 0010) instead of polling. Frontend is a Svelte + Vite + TypeScript SPA with a typed client generated from the OpenAPI spec, no service worker or IndexedDB. All strings in English.

`GET /api/version` is unauthenticated and returns `{"version": "..."}`, the build version of the running binary (`dev` for unversioned builds). Every SPA page shows a footer with the product name and that version, a copyright line matching `LICENSE`, and a link to the GitHub repository; the version is omitted if the request fails.

`GET /api/rulebook` is read-only and unauthenticated. It returns the courses keyed `150`, `60`, `48` and `40` (label, discipline, total shots, stages with distance, expected shots, time and position), the weapon classes per discipline and the ring values (`rings[]` with `ring` and `value`; renamed from `points` to match the rulebook, a breaking change). `internal/rulebook` is its only source, including the course labels; the SPA course dropdowns read from it.

`GET /api/wa1500/search?q=` (admin only) looks up the WA1500 register at the fixed host `https://wa1500.org` (`internal/wa1500`: UTF-8 form POST to `class.php`, response decoded by its declared charset, 10 s timeout, 2 MiB size cap, `LAST,  First` names split into last and first name) and returns `{results:[{waid, first_name, last_name, country, club}]}`. WA1500 provides no sex. Results are cached for five minutes per query and searches are limited to ten per minute (`429`); an unreachable or unusable upstream returns `503` so the client can fall back to manual entry.

`POST /api/shooters/import` (admin only) stores a WA1500 hit locally (ADR 0014). The body is the shooter fields (`waid` required, `first_name`, `last_name`, `country`, `club`, and `sex` chosen by the admin since WA1500 has none) plus optional `update_shooter_id` or `create_new` (mutually exclusive, otherwise `422`). A shooter with the same WAID is updated silently and the call returns `200 {id, action:"updated"}`. Otherwise shooters with the same first and last name (case-insensitive) cause `409 {error:"name_conflict", candidates:[shooter...]}`; the client resends with `update_shooter_id` (must be one of those candidates, else `422`), which updates it and attaches the WAID, or with `create_new: true`. With no match the shooter is inserted and the call returns `201 {id, action:"created"}`. The Shooters page (`/admin/shooters`) has a Search shooters box (server-side `q`) and an Import from WA1500 panel, the shared `Wa1500Import` component: a search box with an explicit Search button, a hit list where each hit needs a sex chosen before Import is enabled, a Name already exists dialog on `409` (update one candidate or Create new shooter), and a manual entry form (Enter manually, shown automatically when the lookup answers 503) that creates the shooter with `POST /api/shooters`. Both manual shooter forms (this one and the Shooters page form) list First name before Last name and show the Normalized name while typing (`web/src/lib/names.ts` mirrors the Go rule; casing applies on every keystroke, whitespace is trimmed and collapsed on blur and submit). The component reports the saved shooter through an `onsaved` callback so the Entries picker can reuse it.

## Backend

Go, chi, SQLite-format storage via Turso Database and `turso.tech/database/tursogo` (`CGO_ENABLED=0`, native library loaded at runtime; see ADR 0005), embedded ordered migrations, strict handler → service → repository layering, `excelize` for xlsx, `certmagic` for ACME. Passwords hashed with argon2id (random salt per user, PHC string, m=19456 KiB, t=2, p=1, rehashed at login when weaker, constant-time comparison, dummy verification for unknown usernames; login answers wrong password and unknown username identically; failed logins are limited per IP and delayed per username, never hard-locked); session cookie `HttpOnly`, `SameSite=Lax`, `Secure` when `BASE_URL` is https.

## Configuration (environment only)

`ADMIN_USERNAME` and `ADMIN_PASSWORD` (16-128 chars), both required only while there are no users, `DB_PATH`, `LISTEN_ADDR`, `BASE_URL`, `TRUSTED_PROXY`, `TLS_CERT_FILE`, `TLS_KEY_FILE`, `ACME_DOMAIN`, `ACME_EMAIL`, `TURSO_GO_CACHE_DIR` (writable path for the extracted native library), `REPLICATION_URL` (empty disables Replication), `REPLICATION_INTERVAL` (default 60s).

## Replication

Optional and off by default. When `REPLICATION_URL` is set, the primary opens its database through the tursogo sync API and pushes to a self-hosted `tursodb --sync-server` on another host, every `REPLICATION_INTERVAL` and when a competition finishes. Push-only: the replica is never merged back. Failures are logged and retried and never block scoring. The sync server has no authentication, so it must only be reachable over a private network; across the public internet use snapshot files instead. Restore is copying the replica's database file to a new primary. See ADR 0005.

TLS modes: plain HTTP (default, behind a proxy); static certificate; ACME via certmagic with certificates stored in the data volume.

## Score log

Whenever a stage changes status (a device or user lock, an accept, a dispute, an unlock, or an admin overwrite of ring counts), the server writes one JSON `info` line to stdout with `msg` and `event` `stage_status` and the stage's new `status` (`open`, `awaiting_acceptance` or `accepted`). A device lock gives `awaiting_acceptance`; a user lock or accept gives `accepted`; a dispute gives `open` with `disputed_at` set and the lock fields empty; an unlock gives `open` with the ring counts kept and `locked_by`, `scorer_name`, `locked_at` and the accepted fields empty. A user's overwrite of ring counts on a stage awaiting acceptance or accepted ends `accepted` and takes it over: the line has `locked_by` and `scorer_name` set to the user's username, and the database records the same, so the original device lock is no longer visible; `locked_at` keeps the original lock time. Fields: `schema_version` (2), `event`, `status`, `emitted_at` (UTC, fixed-width millisecond precision such as `2026-10-19T16:45:14.123Z`), `seq` (integer that strictly increases for every line within a server process, assigned under a mutex so it matches write order), `competition` {`id`, `name`, `date`, `course_of_fire` {`key`, `discipline`, `total_shots`}}, `entry` {`id`, `lane`, `category`, `shooter` {`waid`, `first_name`, `last_name`, `club`}}, `stage` {`number`, `expected_shots`}, `ring_counts` (X, 10, 9, 8, 7, 0, miss), `locked_by` (lane number for a device lock, username for a user lock), `scorer_name` (the username for a user lock), `locked_at`, `accepted_by`, `accepted_at`, `disputed_at`. The line is written after the database write succeeds; a log failure never fails the transition. Editing a competition, an entry or a shooter re-emits `stage_status` for every affected stage that is not open (a shooter edit covers all of that shooter's entries across competitions) as currently recorded and with a new `emitted_at` and `seq`; open stages emit nothing. Replay: the last line per competition, entry and stage by (`emitted_at`, `seq`) wins; `seq` restarts at 1 after a server restart, which is safe because `emitted_at` is compared first, and a final `open` line means the stage is open with its ring counts. Entries with no status change are not recoverable, and lines contain personal data. The `restore` subcommand (`matchmark restore [file]`, stdin when no file is given; no `ADMIN_USERNAME` or `ADMIN_PASSWORD` needed) parses the log, skips non-score and malformed lines (including an unknown course key or status, a `locked_by` that is neither a positive lane number nor a non-empty username on a locked stage, or an `emitted_at` not in the fixed-width layout) with a count, rejects any other `schema_version` (including the retired version 1 `stage_locked` and `stage_unlocked` lines), applies the replay rule with context taken from the latest line, and prints a summary of the competitions, entries and stages. Without `--apply` it is a dry run and writes nothing. With `--apply` it opens the database from the server configuration (`DB_PATH`), runs migrations and recreates each competition (status `finished` when every stage is accepted, otherwise `active`), its shooters (matched by WAID, else by name and club), entries and stages with ring counts, status, `scorer_lane` (NULL for a user lock), `scorer_name`, `locked_at` and the accepted fields, keeping the original competition and entry ids. It refuses a database that already contains competitions or shooters and changes nothing; all competitions are written in one transaction, so a failure changes nothing; flags may follow the file path; `--merge` instead applies only data whose ids match or are new, lists conflicts (a differing competition, entry, or non-open stage counts, status, `locked_by`, `scorer_name` or `locked_at`) and never overwrites them. It is idempotent by ids and leaves stages that are not open untouched. Sex and country are not in the log, so restored shooters get sex `M` and an empty country. Unscored entries, devices and pairings are not restored and the command says so, including that devices must be re-paired before scoring continues; awaiting-acceptance stages are restored intact, a dispute-reopened stage is restored open with its hits, and the current stage is the lowest stage not accepted by every restored lane. See ADRs 0007 and 0013.

## Audit log

Every mutation, login, failed login, failed password change, report download, backup download and `reset-password` run is written to the `audit_log` table (migration 014) and, after the database write succeeds, to stdout as a JSON `info` line with `msg` `audit`. The service layer writes both, so every entry point is covered; a write failure is logged and never fails the request. Fields: `time` (UTC), `user_id` (absent for devices and failed logins), `username` (the username at the time of the event; the attempted username for a failed login; `device` for a paired device), `action`, `target`, `details`, `ip` (the client IP, honouring `TRUSTED_PROXY`). Actions: `competition.create|update|status|visibility|delete`, `shooter.create|update|delete`, `entry.add|update|withdraw|delete`, `stage.set_counts|lock|accept|dispute|unlock`, `competition.next_stage|accept_all`, `club.update|logo.set|logo.delete`, `device.pair|revoke`, `user.create|deactivate|reactivate|reset_password|set_role|set_backup_permission|change_password|change_password_failed`, `login`, `login_failed` (details `throttled` when the per-IP limit answered), `report.download` (details `xlsx` or `csv`) and `backup.download`. Counts entered and locks made by a paired device have actor `device` and details `lane <n> competition <id>`; `user.reset_password` from the `matchmark reset-password` command has actor `cli`. A failed password change (wrong current password) is recorded as `user.change_password_failed`. Only successful changes are recorded. Targets look like `competition:3`, `competition:3/entry:7/stage:1` or `user:2`. Entries are kept forever; database triggers reject updates and deletes and there is no write or delete endpoint. `GET /api/audit-log` (admin only; users get 403) returns `{entries, total, page, page_size}` newest first, filtered by `user` (case-insensitive username), `action` (exact), `from` and `to` (`YYYY-MM-DD`, UTC, inclusive), with `page` and `page_size` (default 50, maximum 200); invalid parameters answer 422. The admin UI shows it at `/admin/audit` (link visible to admins only). Seeding the first admin is not audited. See ADR 0011.

## Delivery

Repository root: `Dockerfile`, `docker-compose.yml` (app plus `./data` volume only), `docs/`, `GLOSSARY.md`, `README.md`, `AGENTS.md`. Code in `source/` (Go module root; `source/web/` for the SPA). Dockerfile: Alpine Node stage builds `web/`, Alpine Go stage embeds `web/dist` and builds with `CGO_ENABLED=0 -tags musl`, final Alpine 3.24 image (the tursogo native library needs a libc to `dlopen`) running non-root with `TURSO_GO_CACHE_DIR` on a writable path. Supported targets: linux/amd64 and linux/arm64 (64-bit Pi OS only) as image and binary; darwin/amd64, darwin/arm64 and windows/amd64 as unsigned release binaries (ADR 0012). The admin UI offers a database backup download; it uses `VACUUM INTO` with a string literal path, which Turso Database supports (bound parameters are rejected).

CI (GitHub Actions) builds, tests and smoke-tests the image natively: `ubuntu-latest` for amd64, `ubuntu-24.04-arm` for arm64, no QEMU, plus a build-only `macos-latest` job. The smoke test opens a database inside each image because a library-loading failure only shows at runtime.
