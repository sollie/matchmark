# MatchMark v2 Spec

Scoring for WA1500/PPC competitions at a single club. Vocabulary is in `GLOSSARY.md`; decisions are in `docs/adr/`.

## Scope

In: competitions, a persistent shooter registry, lane-paired scoring devices, live spectator view, results report (`.xlsx`), internal detailed CSV, admin database backup.

Out for v1: classification and ranking, relays, 60/48 beyond course data, offline operation, PDF/JSON export, multi-club hosting, accounts for scorers.

Future: relays; DNS-01 and other ACME challenge methods; CDN-hosted frontend; multi-club tenancy; offline queue; classification.

## Users and flow

- Admin (named user with username and password, 12-hour cookie session; the first admin is seeded from `ADMIN_USERNAME` and `ADMIN_PASSWORD` when there are no users): creates a match, picks the course of fire, adds entries from the shooter registry (or creates new shooters), assigns lanes and categories, opens pairing, sets spectator visibility, watches progress in the control room, starts each next stage, accepts on a shooter's behalf, unlocks and corrects stages, finishes the match, downloads the results report and detailed CSV from the match list (buttons shown only for finished matches). A user changes their own password at `/admin/password` by supplying the current one (new password 16-128 characters); this ends their other sessions. A user whose password was reset (temporary password) is flagged and can reach only change-password and logout (other endpoints answer 403 `password_change_required`) until it is changed. Admins manage users at `/admin/users` (API `GET`/`POST /api/users`, admin only; regular users get 403): create a user with a username, a role (`admin` or `user`) and a temporary password (16-128 characters) that the user must change at first login, and list users with role and status. Per user: `POST /api/users/{userID}/deactivate` and `/reactivate` (a deactivated user cannot log in and their sessions end at once), `POST /api/users/{userID}/reset-password` (temporary password, forces a change at next login, ends sessions) and `PUT /api/users/{userID}/role` (promote or demote; demotion ends sessions and clears the backup permission) and `PUT /api/users/{userID}/backup-permission` (`{"can_download_backup": bool}`; admins only, a regular user answers 422). The seeded admin has the backup permission; `GET /api/admin/backup` answers 403 `backup_not_permitted` to users and admins without it, and the UI hides the Backup menu entry. The last active admin cannot be demoted or deactivated (409); unknown users answer 404. Users are never deleted. Usernames are 3-32 characters from `a-z`, `0-9`, `.`, `_`, `-`, stored lowercase, unique case-insensitively and never reused; a taken name answers 409. Regular users cannot manage users or take a backup but can use every match, shooter and entry feature. `GET /api/admin/session` returns the signed-in `username`, `role` and `can_download_backup`.
- Scorer (device): opens a pairing link once, then sees only "Scoring lane N: name", enters ring counts for the current stage and locks it, then waits (Lock stage stays disabled while the entered ring counts differ from the saved ones or no valid counts are saved, and a status line says "Unsaved changes: press Save, then Lock stage." or "Saved ✓"); as a shooter the device also accepts or disputes its own result, and after a dispute the scorer re-scores the stage.
- Spectator (no login): live standings under one slim status row that wraps on small screens (match picker, match status, `Stage N of M` from the snapshot's `current_stage` and `total_stages`, the snapshot's `status` keeping the match status (and the finished links) current without reloading the list, the course's stage count from the rulebook, an `x/y accepted` count for the current stage that excludes withdrawn entries, and the Live or Offline badge with the last update time; a finished match shows `Finished` instead of the stage position and count; there are no progress bars and no separate progress endpoint), with each shooter's stage state (`not_started`, `in_progress`, `awaiting_acceptance`, `accepted`; a disputed stage reopens as `in_progress`, and only an accepted stage shows its score), always visible and shown as a coloured cell with a title, an accessible label and a legend; the score itself follows the stage-scores visibility flag, other fields follow admin's per-match field visibility.
- Results view (no login): `/results` picks among finished matches (newest first) and `/results/{id}` is the deep link; the spectator page links to it once the match is finished. A printable sheet (print stylesheet hides the site chrome) shows the club logo and name, match name, date and course, then per category a table of rank, shooter, WAID, each segment's score (columns headed by the segment names), total and X count, then a score card per shooter (one column per segment plus a total, rows X, 10, 9, 8, 7, 0 and M; only accepted segments filled, shown only while ring counts are visible), ranked by total then X count (rank shared only when both are equal). Withdrawn entries are listed below the ranked rows of their category as DNF (did not finish): unranked, with the scores of their accepted segments and "DNF" in place of the total. The sheet ends with a New shooters list (shooters without a WAID). It carries no classification or medals and honours the visibility flags: hidden names also hide WAID and the new shooters list, hidden segment scores omit the segment columns, hidden ring counts omit X. `GET /api/spectator/matches/{id}/results` returns `{match{id,name,date,course,course_label}, segments[], categories[{category, rows[{rank, last_name?, first_name?, waid?, club?, country?, segments[{segment, score?, ring_counts?}], total, x_count?}], did_not_finish[{last_name?, first_name?, waid?, club?, country?, segments[{segment, score?}]}]}], new_shooters[{last_name, first_name, category, club?, country?, total, x_count?}]}` and answers 404 unless the match is finished.

The global site header carries the MatchMark logo, the club badge (right-aligned; below about 480px the club name is hidden when a logo exists, and truncated with an ellipsis otherwise) and, at the far right, an account icon of at least 44px. On public routes (spectator, results, scorecard) it is a person-circle link to `/admin` named "Sign in"; it makes no session request. On the scorer route (paired devices) it is not shown. The spectator page has no separate Admin link. On admin routes, once signed in (and not forced to change the password), the slot is the account menu: a button (`aria-haspopup="menu"`, `aria-expanded`) that opens a panel of native links, closes on Escape, outside click and navigation, and carries `aria-current="page"` while Users, Club, Audit log or Change password is open. The panel header shows the signed-in username and role; admins see an Administration group (Users, Club, Audit log, and Backup when `can_download_backup`) and everyone sees an Account group (Change password, Sign out). The admin tab bar holds Matches and Shooters, plus a right-aligned, muted "Spectator view ↗" link that opens the spectator page in a new tab. Sign out returns to `/`; a successful sign-in always lands on `/admin`.

## Remote-controlled screens (ADR 0020)

A spectator display can opt in to remote control and become a Screen: it registers (`POST /api/spectator/screens`), receives a random 128-bit token (stored hashed, kept in `localStorage`) and shows a 6-character code. It appears in the admin list at `/admin/screens` only after an admin approves the code and names it (default "Screen N"). Registration is capped and rate limited per client IP. An unmanaged screen shows the most recently started match (`matches.activated_at`), or a waiting view if none, and never defaults to a draft. An admin assigns any non-finished match to a screen (`PUT /api/screens/{id}`) or applies one match to all approved screens (`PUT /api/screens/assignment`, a one-time write). A draft match shows a waiting view with no name, date, course or participants and is pushed to the screen when the match starts. The token-header stream `GET /api/spectator/screens/stream` carries only `{state: waiting|match, match_id, approved}`, where `approved` is false while the screen is pending an admin's approval (see Screen lifecycle in `GLOSSARY.md`: pending, approved, assigned); the screen then uses the per-match spectator stream, so visibility flags apply. A finished match stays assigned and shows the final standings; a deleted match falls back to the default. A viewer leaves with `DELETE /api/spectator/screens/self`; a removed screen gets 401/410 and reverts. A screen is online while connected or seen within 2 minutes, and is purged after 24 hours unseen.

## Club settings

One row in `club_settings`: the club `name`, the `logo` BLOB with its `logo_content_type`, and a `version` that increases on every edit. Admins edit it at `/admin/club`. `GET /api/club` is public and returns `{name, has_logo, version}` (name empty when unset). `PUT /api/club` (admin only) takes `{name}`, trims it and accepts at most 100 characters. `PUT /api/club/logo` (admin only) takes the raw image as the request body with `Content-Type` `image/png` or `image/jpeg`; SVG and every other type, an empty body, a body over 512 KB, a body whose bytes do not match the declared type and an image over 2048 by 2048 pixels answer 422. `DELETE /api/club/logo` (admin only) removes it. `GET /api/club/logo` is public, answers 404 without a logo and sends `Cache-Control: no-cache`; clients append `?v=<version>` as a cache-buster, which the server ignores. The settings live in the database, so Backup and Replication cover them. Changes are written to the Audit log (`club.update`, `club.logo.set`, `club.logo.delete`). Regular users get 403 on every write.

## Results PDF

`GET /api/matches/{id}/results` renders the Results view as a PDF on demand (ADRs 0015 and 0016), as standings only, with the segment names as column headings and no per-shooter ring counts (those stay in the Results view, the scorecard copy and the CSV). It is public, honours the visibility flags like the Results view and answers 404 unless the match is finished. `GET /api/admin/matches/{id}/results` needs an admin session, shows every column whatever the flags and is audited as a `report.download` with details `pdf`. `format` defaults to `pdf`; any other value answers 422. The document is A4 portrait. Categories flow one after another on shared pages (a category heading is never left alone at the bottom of a page; long categories continue on the next page) and a final page lists new shooters. Each category heading carries its shooter count; each shooter is one compact row of rank, name, WAID (small and muted), club, country, segment scores, total and X count, with the top three ranked rows lightly tinted. Text is 7 pt on a 4.2 mm row pitch. Column widths are measured from the longest value in each column (and, for segment headings, the longest word) so numbers, WAID and country never wrap; the Shooter and Club columns take the spare width, or give up the shortfall. Cells that do not fit wrap at word boundaries and the row grows; text past three lines ends with an ellipsis. Segment headings keep their full names on up to two lines. DNF entries follow the ranked rows with "DNF" in the Total column. Every page repeats a header with the club logo and name, the match name, date, course and the participant count (ranked and DNF entries), and a footer with the MatchMark icon and a clickable "Scored with MatchMark · https://github.com/sollie/matchmark" beside the generation time and "Page x of y". The printed Results view ends with the same credit line; the `.xlsx` and the scorecard copy carry none. A missing club name falls back to "MatchMark" and a missing club logo to the MatchMark icon. Responses are `application/pdf` with `Cache-Control: private, no-cache` and `Content-Disposition: attachment; filename="<match name>-<match date>-results.pdf"`; nothing is stored. Both endpoints sit behind the render guard; the admin one is not coalesced, so every request renders and is audited. The Results view has a Download PDF button and the admin match list has a PDF button beside XLSX and CSV for finished matches.

## Scorecard copy

`GET /api/scorer/scorecard/{matchID}/{lane}` renders the Scorecard of the entry on that lane as a PNG on demand (ADRs 0015 and 0016). It is public, outside the device middleware and ignores the spectator visibility flags. `format` defaults to `png`; any other value answers 422. It answers 404 for an unknown or unfinished match, an empty lane and a withdrawn entry. The card shows the shooter, WAID when known, category, lane, match name and date, the club logo and name (from Club settings), one column per scoring segment (named as on the paper score card) plus a total column, and rows for the ring counts X, 10, 9, 8, 7, 0 and M, the score, the scorer (the range admin for admin-scored segments) and the shooter's name. Segment names come from `internal/rulebook`; only accepted segments are filled in and counted, others stay blank. The response is `image/png` with `Cache-Control: private, no-cache`; nothing is stored. The SPA route `/scorecard/{matchId}/{lane}` is public and shows the shooter and the scorer of each accepted stage as text (from the summary endpoint below), the PNG (image URL with a `v` cache-buster, alt text naming the shooter and lane) with a prominent Download PNG link (`download=1`), or a clear message when the card is not available (404); on `429` or `503` (render limits) it asks to try again shortly and retries after the `Retry-After` delay, and an image that fails to load gets the same treatment or a retry button; the spectator standings link to it per lane once the match is finished. `download=1` adds `Content-Disposition: attachment` with `<match name>-<match date>-lane-<n>.png` (same name rules as the report downloads).

`GET /api/scorer/scorecard/{matchID}/{lane}/summary` returns `{shooter, lane, scorers: [{segment, segment_name, scorer}]}` as JSON, one item per accepted segment (`Range admin` for admin-scored segments). It has the same availability as the card (404 unless the match is finished and the lane has a kept entry), is public and ignores the visibility flags; the SPA uses it so the names are text rather than only pixels.

The endpoints run behind the render guard (`handler.RenderGuard`, ADR 0016): at most 4 renders at once with a short queue (`503` with `Retry-After` when full), identical public requests share one render (admin PDF requests do not, so each is audited), and each client IP may make 20 requests per minute per resource (`429` with `Retry-After`). The client IP honours `TRUSTED_PROXY`. Edge rate limiting is left to the CDN.

## Scoring rules

- Score lane is the next manned lane after the scorer's own lane, wrapping, derived server-side from the device's pairing and current entries. A paired lane is always manned.
- A match with one manned lane requires admin scoring.
- Everyone shoots in step on the match's current stage (`matches.current_stage`). Activation starts at stage 1. `POST /api/matches/{id}/next-stage` (admin) moves the pointer by one and answers 409 until every manned, non-withdrawn lane has accepted the current stage, and when the match is not active or is on its last stage. Devices can score, lock, accept and dispute only the current stage (409 otherwise); the admin can still edit, lock, accept and unlock any stage, and an admin unlock after the pointer moved on reopens that stage without moving the pointer. The last acceptance of the last stage (by a device or the admin) finishes the match through the normal finish path (pairings revoked, replication push, audit). Unlocking a stage of a finished match leaves it finished. Back to draft: `POST /api/matches/{id}/back-to-draft` (admin) moves an active match to draft. It answers 409 unless the match is active and no entry, including unlocked and withdrawn entries, has stored hit counts; the check and the status change happen in one transaction, so a scorer hit that loses the race gets the normal draft `not_started` response. The match then behaves like any draft: devices show `not_started` and keep their pairings, spectators and Screens hide the match and Screen assignments are kept, lanes and `current_stage` are unchanged (the score lane is recomputed on start), and entries, lanes and match fields can be edited as in any draft, with the course locked while entries exist. "Start match" works as usual and its time becomes the new `activated_at`, which the most recently started match uses. Audit: `match.back_to_draft`. Entries can be added and moved to another lane only while the match is a draft (an active match still allows changing an entry's category; a finished one allows nothing). Withdrawing is allowed in a draft or at the gate (current stage fully accepted, before the next stage starts) and never once finished; a withdrawn entry is flagged and keeps its results, and later stages re-target to the next manned lane. Matches keep independent pointers.
- Hits per stage are seven counts (X, 10, 9, 8, 7, 0, miss) that must sum to the stage's expected shots. X scores 10. 0 and miss score 0.
- A stage is `open`, `awaiting_acceptance` or `accepted`. A device lock leaves the stage awaiting acceptance with its hits frozen and records the scorer's lane and name. An admin lock (as the signed-in user) or an admin accept (`POST .../stages/{stage}/accept`, only from awaiting acceptance, else 409) makes it accepted. Only the admin can unlock (back to open, hits kept) and edit; an admin edit of an awaiting or accepted stage ends accepted and takes the stage over. Standings, the results report and the CSV count only accepted stages; the admin entries list shows every stage's score and status. The shooter accepts or disputes from their own device: `POST /api/scorer/stages/{stage}/accept` and `.../dispute` act only on the stage of the device's own lane, answer 409 unless it is awaiting acceptance and 403 for a stage the device itself locked. A dispute reopens the stage as `open` with hits kept and sets `disputed_at`, which the next lock clears; accept records the lane as `accepted_by`. The scorer snapshot carries a server-derived `phase`: `scoring` while the current stage of the device's score lane is open, `next_stage` when the admin has started the stage (`stages.started`) and the scorer has not yet saved hits or locked it, so a re-pair or restore never shows it (the device shows a banner and a Continue button), `not_started` while the match is a draft (the device can be paired before the start and shows a waiting screen with only its lane, no shooter name; the stream switches it to scoring on activation; writes answer 409), `finished` once the match is finished (the pairing is revoked but the session still answers with only `lane` and `phase`, and an open stream ends with a final `finished` snapshot, so the device forgets its token at once and navigates to its own lane's scorecard page (`match_id` and `lane` are in every session); a stream request with the token of a finished match answers 410, which the client treats as terminal; writes answer 409). The client resets its reconnect backoff only after a stream has stayed open for several seconds, so a connection that closes at once keeps backing off, otherwise `waiting`, or `needs_acceptance` with an `acceptance` object (stage, ring counts, total, scorer name) when the device's own stage awaits acceptance, so a shooter who also scores sees the request only after locking their own scoring. Each snapshot stage carries its ring counts, a `disputed` flag and, for courses with groups, its `part` (also on `acceptance`), derived server-side from the rulebook, so the device headings and banners read "Stage 4 · Match 3" for the 150 course and plain "Stage 4" otherwise; so the Disputed notice and the prefilled values survive a reload. The device shows a waiting screen with a banner and a Review result button, a read-only result (total, X count, stage chip, per-ring bars) with Accept and Dispute, where Dispute asks for a one-tap confirmation (Confirm dispute or Cancel) before anything is sent, and the Disputed notice; banners only, no push, sound or vibration. Accept and dispute are written to Stage events, the Score log and the Audit log (`stage.accept`, `stage.dispute`). The session and the match JSON carry `current_stage`; an active match's admin page shows the control room (below).
- Dispute history: `GET /api/matches/{id}/stage-events` (admin; 404 for an unknown match, 422 for a bad `stage`) returns `{events, scorers}`. `events` are the Stage events oldest first (`id`, `time`, `stage`, `entry_id`, `event` of `locked`, `accepted`, `disputed`, `accepted_all` or `unlocked`, `actor_type` `device` or `user`, `actor_name`, `shooter_name`, `scorer_name`). Device events carry the shooter and scorer resolved from the pairing when they happened. The optional exact filters `scorer`, `shooter` and `stage` narrow the events, and `scorers` holds `locks` and `disputes` per scorer name over the filtered events (admin lock and accept events carry no scorer, so the admin is never counted) so a scorer who is corrected on every stage stands out. The admin page shows it as the Dispute history section with scorer, shooter and stage filters, for every match that is not a draft.
- Control room: `GET /api/matches/{id}/control-room` (admin; 409 for a draft) returns `current_stage`, `can_start_next`, `can_accept_all` and one row per manned, non-withdrawn lane with `lane`, `entry_id`, `shooter_name`, `scorer_name` (the locking scorer, else the derived scorer, empty when the lane is admin-scored), `status`, `disputed`, `disputes` (disputes across all stages), `paired` and `connected`. `connected` is best-effort: it is true while the lane's device holds an open scorer stream, is kept in memory only, never stored, and is labelled best-effort in the UI. `can_start_next` is true at the gate; `can_accept_all` is true when no manned lane is open and at least one awaits acceptance. `POST /api/matches/{id}/accept-all` (admin) accepts every awaiting stage of the current stage in one transaction (stage events `accepted_all`, audit `match.accept_all`, auto-finish on the last stage) and answers `{accepted}`; it answers 409 while any manned lane is open or the match is not active. The grid updates live from the admin stream, including when a device connects or disconnects. The match page offers Back to draft, shown only while the match is active and no hit counts are stored, behind the confirmation "Return this match to draft? Devices will show 'not started' and spectators won't see the match until you start it again. Only possible while no hits are entered." The page offers Start next stage and Accept all (each disabled unless allowed) and per-row Accept and Unlock, which work for lanes without a paired device; an admin lock of such a lane is final.
- The admin entries list shows each stage's score and shots entered, and carries the seven stored ring counts of every segment (`x`, `10`, `9`, `8`, `7`, `0`, `miss`, the same shape as the scorer payload; a segment without counts has all seven at 0 and `shots_entered` 0, since saved counts must sum to the segment's shots), for open as well as awaiting-acceptance and accepted stages. An open stage with all expected shots entered is shown as "Scored, not locked".
- Course data and shot counts live in one `rulebook` package and match rulebook Issue 2026-01-01 §7. The 150 course is 10 stages grouped as Match 1 (7 yd, 15 yd), Match 2 (25 yd), Match 3 (50 yd), Match 4 (2 × 25 yd), Match 5 (7 yd, 25 yd, 50 yd, 25 yd × 6). Each stage of the 150 course carries its group as a Part (`part` in `GET /api/rulebook`, e.g. `Match 3`); courses with no groups omit it. The admin entries list shows "Stage 4 · Match 3" labels (column title and mobile cell label) and the scorecard image shows "4 · Match 3"; the scorer device screens use the same label; other courses show plain stage numbers. Stages stay numbered in the rulebook; scoring segments (above) are what is recorded.

## Scoring segments (ADR 0021)

The system scores at the paper's "Score the target" points, not per stage. A scoring segment is a run of stages between two such lines; one set of seven ring counts (X, 10, 9, 8, 7, 0, M) is recorded per segment and must sum to the segment's shots. Lock, accept, dispute, the gate, the control room, the current segment, the Dispute history and the Score log all work per segment, and the scorer screen does not show stage distances. The 150 course has six segments: Match 1 (24 shots), Match 2 (18), Match 3 (24), Match 4 (24), Match 5 · Stage 1+2 (30) and Match 5 · Stage 3+4 (30). The 48, 60 and 40 courses have two, Stage 1+2 and Stage 3+4, with 18 + 30, 30 + 30 and 15 + 25 shots; score-card names win over the cheat sheet's Match 1/Match 2. Segment names, stage lists and shot counts come only from `internal/rulebook` and are served as `segments[]` (`number`, `name`, `stages`, `shots`) of each course in `GET /api/rulebook`. The scorecard copy, Results view, Results PDF and spectator screens show one column per segment with rows X, 10, 9, 8, 7, 0, M and a total. Withdrawal stays allowed between segments; the scorers of a withdrawn entry are rerouted to the next manned, non-withdrawn lane from the following segment on. An admin edit works in any non-draft match. In the admin entries view, Edit on a scoring segment opens a modal dialog titled with the shooter and segment name (for example "Mike Anderson, Match 3"); focus moves to the first ring-count input and returns to the Edit button on close, Enter in an input does not submit, and Cancel or ✕ closes it. The dialog shows the stored counts read-only (the seven counts, the total against the expected shots and the status, or "No counts entered yet" when none) and pre-fills the inputs with them. Save counts and Save and lock close the dialog on success; on failure it stays open with the inputs kept and the error shown inside it. Until the follow-up work (#424 to #426) lands, the stage wording in the sections below describes the behaviour being replaced and reads as segment.

## Competition and Match (ADR 0017)

- Competition: name, start date, end date (one day by default); no stored status. It holds one or more Matches and every Match belongs to exactly one Competition. A Match's date must fall inside the Competition's range, and a range change that would leave a Match outside it is rejected. Admins manage Competitions at `/api/competitions` (list, create, read, update, delete; each answers with `match_count`, derived from its Matches). A Competition with Matches cannot be deleted (409). Creating a Match picks an existing Competition (`competition_id`), creates one together with the Match (`competition`), or, with neither, creates a one-day Competition from the Match; a Match's Competition cannot be changed afterwards. The Match list in the admin UI is grouped by Competition. Changes are audited as `competition.create|update|delete`.
- Match: one course, one date, status draft/active/finished, visibility flags, entries, lanes, stages and results. A shooter has at most one entry per Match.
- Rulebook mapping: Competition is the rulebook's announced competition (statement 1326, `docs/references/rulebook2026-amendments.md` A1); Match is the rulebook's match. The 150 course's "Match 1" to "Match 5" are called Parts and are labels from `internal/rulebook`.
- The limit of one Revolver 1500, one Pistol 1500 and one Optical Sight match per shooter per competition (statement 1326, re-entry matches) is not enforced, because the club runs no re-entry matches.
- Admin downloads per Competition (planned, #351) are zips of the per-Match reports, rendered on demand and never stored (ADR 0016): xlsx, CSV and PDF zips, and a download-all zip with a folder per Match. Unfinished Matches are skipped and listed in `SKIPPED.txt`. The Combined 1500 workbook (#421, ADR 0022) is a separate, bare `.xlsx` for the whole Competition.

## Match model

- Match: name, date, course of fire (150 default; 60 and 48/40 selectable; no partial courses), status draft/active/finished, spectator visibility flags. A draft match can be edited from its page (name, date and course); the course is locked once it has entries. An active or finished match can only be renamed: `PUT /api/matches/{id}` answers 409 unless its date and course equal the current ones. The audit detail of `match.update` records the old and new name, and locked segments are re-emitted to the Score log with the new name.
- Shooter: last name, first name, country, club, optional WAID. Persistent (shooters carry no sex, ADR 0018). Names are stored as a Normalized name: last name uppercase, first name with each word capitalised (also after a hyphen or apostrophe), whitespace trimmed and collapsed, Unicode-aware (`service.NormalizeLastName` and `service.NormalizeFirstName`). `POST /api/shooters` and `PUT /api/shooters/{id}` answer 422 for a name that is not already normalized; `POST /api/shooters/import` normalizes the WA1500 names before matching and saving. The rule lives in `internal/names`. A shooter without a WAID is a new shooter. `GET /api/shooters` takes optional `q` (case-insensitive partial match on WAID or on first and last name in either order; `%` and `_` are literal) and `limit` (1-100; 422 otherwise; defaults to 20 when `q` is given, otherwise all shooters); `include_archived` (`true` to include archived shooters, which are hidden by default); every item carries `archived` and `entry_count`, the shooter's entries in any match, withdrawn ones included. `GET /api/shooters/{id}` adds `matches` (`id`, `name`, `date`, `status`, newest first). `DELETE /api/shooters/{id}` answers 409 when the shooter has any entry, including a withdrawn one or one in a finished match; the server check is authoritative. Duplicates are merged with a Shooter merge (ADR 0019, admin only): `GET /api/shooters/{id}/merge-preview?target_id=N` returns `{source, target, entries, conflicts, waid_conflict, resulting_waid, can_merge}` (`entries` are the source's entries that move; `conflicts` are matches both shooters are entered in) and `POST /api/shooters/{id}/merge` with `{target_id}` re-points every entry of the source to the target, refreshes the shooter name stored on stage events, deletes the source in one transaction and answers `{target_id, moved_entries}`. The target wins on every field; the source WAID carries over only when the target has none. The merge answers 409 `{error:"merge_blocked", ...preview}` when both shooters have different WAIDs or both have an entry in the same match, 409 `{error:"shooter_archived"}` (merge and preview) when the target is archived, 422 when source and target are the same and 404 for an unknown shooter. Finished matches are included and reports already sent are not regenerated. Archiving an already archived shooter, or unarchiving an unarchived one, changes nothing and is not audited. The merge checks the blockers again inside its transaction, so a change between preview and merge cannot slip through. Success is audited as `shooter.merge` (target `shooter:<source>`, details `into shooter:<target>, <n> entries moved, WAID <resulting WAID>`), pushes a live update to every stream and re-emits the locked stages of the target. The Shooters page has a Merge into… button per row that opens a dialog: pick the target (archived shooters are not offered), review the entries to move, the conflicts and the resulting WAID, tick "I understand this cannot be undone" and confirm. The shooter list disables Delete when `entry_count` is above 0 and shows "Entered in N matches", which expands to links to each match's admin page. The entry form picks the shooter through a search combobox (Shooter) that queries the registry after a short debounce, lists name, WAID, club and country, supports arrow keys, Enter and Escape, hides shooters already entered and shows "No match" when nothing is found. While a query is typed the combobox also lists Archived shooters with an Archived badge; they cannot be selected.

Archived shooter (GLOSSARY.md): `POST /api/shooters/{id}/archive` and `/unarchive` (admin only, audited as `shooter.archive` and `shooter.unarchive`, live update to all views; unknown shooters answer 404) set the `archived` flag stored in `shooters.archived` (migration `002_shooter_archive.sql`). An archived shooter stays in past results, reports and the audit trail and its WAID stays reserved. The default shooter list and the entry pickers hide it; the Shooters page shows it with an Archived badge when searched, with Archive and Unarchive buttons per row. Adding an archived shooter to a match answers `409 {error:"shooter_archived"}`; the entry form shows "This shooter is archived" with an inline Unarchive button. Existing entries are untouched. The delete rule is unchanged (409 when the shooter has any entry) and the Shooters page adds "Archive or merge this shooter instead." beside the disabled Delete.
- Entry: shooter, category (Revolver, Pistol, Revolver OS, Pistol OS, Carbine), lane, withdrawn flag. `internal/rulebook` defines the categories each course allows: 150 shots Revolver, Pistol, Revolver OS, Pistol OS and Carbine (shot on reduced WA1500-29 targets; scoring is unchanged); 60 shots Revolver, Pistol, Revolver OS and Pistol OS; 48 shots Revolver and Pistol; 40 shots Revolver only; Carbine only on 150. Carbine entries share the match and lane rotation with the other categories. `GET /api/rulebook` carries them as `courses[].categories` (string array). Creating or updating an entry with a category the course does not allow answers 422; existing entries are not migrated. The add-entry and edit-entry Category dropdowns list only the categories of the match's course; the add form falls back to the first allowed category when the selection is not allowed.
- Stage per entry, created when the entry is added: expected shots, seven ring counts, status (`open`, `awaiting_acceptance`, `accepted`), `accepted_by`, `accepted_at`, `disputed_at`, scorer. Every status change is also appended to `stage_events` (event, actor type and name, scorer, shooter, time).
- Device pairing: token, match, lane, revoked flag.

## Results report

Filled in from the embedded template (`docs/references/results_reporting_template.xlsx`) using `excelize`. One sheet per category; match name and date in the header; known shooters as WAID + total result, extra rows inserted as needed; new shooters in the "New shooters" block with last name, first name, sex, country, club, result; the sex cell is left empty for the receiving club representative (ADR 0018). The template is a replaceable embedded file.

Combined 1500 workbook (#421, ADR 0022): `GET /api/competitions/{id}/results.xlsx` (admin) returns one bare `.xlsx` for the Competition, named `<competition name>-<start date>-1500.xlsx`, filled from the same template. It covers the finished Matches whose course has the 1500 discipline (selected through `internal/rulebook`, never a hard-coded course key); other courses and unfinished Matches are left out. Every category sheet is kept; `A1` is the Competition start date and `B1` the Competition name. Each sheet has one known-shooters block and one new-shooters block with rows added as needed, using the same entry selection, totals and sort as the per-Match report, ties broken by Match ID. A shooter who shot several Matches has one row per Match, not merged. No finished 1500 Match answers 422 "nothing to report" and an unknown competition 404. The endpoint sits behind the render guard (not coalesced) and is audited once as a `report.download` with target `competition:<id>` and details `xlsx 1500`. The competition section of the admin match list shows a 1500 XLSX button only when a finished 1500 Match exists, warns which unfinished 1500 Matches will be left out, and keeps the XLSX zip button for per-Match files.

The `.xlsx` report and the detailed CSV are downloaded with buttons in the admin match list, shown only for finished matches; the endpoints themselves do not check the status.

The results reporting template (`docs/references/results_reporting_template.xlsx`) has one `Result:` total per shooter and no per-Part subtotals, so the `.xlsx` is unchanged. An internal detailed CSV lists ring counts per scoring segment (columns `segment` number and `segment_name`) per entry for the club's own records; only accepted segments are counted (others appear with zero counts and `accepted` false) and the same holds for the `.xlsx` report. The CSV starts with a UTF-8 byte-order mark so spreadsheet applications show non-ASCII names correctly. Both downloads are named `<match name>-<match date>.<ext>` (for example `Test2-2026-10-20.xlsx`): characters other than letters, digits and `_` collapse to a single `-`, names are capped at 60 characters, an empty name becomes `results`, and non-ASCII letters are sent via an RFC 5987 `filename*`.

Competition downloads: `GET /api/competitions/{id}/results.zip?format=xlsx|csv|pdf|all` (admin) bundles the per-match reports of the competition, generated on demand and never stored (ADR 0016). `xlsx`, `csv` and `pdf` give one file per finished match named `<match name>-<match date>-<course>.<ext>`; `all` gives one folder per match holding all three formats. Unfinished matches are skipped and listed in `SKIPPED.txt` in the zip. A missing or unknown `format` answers 422 and an unknown competition 404. The endpoint reuses the per-match renderers and sits behind the render guard (not coalesced, so every download is audited); it is audited once as a `report.download` with target `competition:<id>` and details `zip <format>`, and the zip is named `<competition name>-<start date>-<format>.zip`. The competition section of the admin match list has XLSX zip, CSV zip, PDF zip and Download all buttons.

## API and frontend

JSON REST API under `/api`, documented with OpenAPI; admin and spectator endpoints separated; spectator endpoints are unauthenticated. The spectator snapshot carries `current_stage`, and each standing's stage entry carries `state`. Spectator, admin and scorer screens receive live updates over server-sent events (one stream per role and match, see ADR 0010) instead of polling. Frontend is a Svelte + Vite + TypeScript SPA with a typed client generated from the OpenAPI spec, no service worker or IndexedDB. All strings in English.

`GET /api/version` is unauthenticated and returns `{"version": "..."}`, the build version of the running binary (`dev` for unversioned builds). Every SPA page shows a footer with the product name and that version, a copyright line matching `LICENSE`, and a link to the GitHub repository; the version is omitted if the request fails.

`GET /api/rulebook` is read-only and unauthenticated. It returns the courses keyed `150`, `60`, `48` and `40` (label, discipline, total shots, stages with distance, expected shots, time and position, and segments with number, name, stage numbers and shots) and the ring values (`rings[]` with `ring` and `value`; renamed from `points` to match the rulebook, a breaking change). `internal/rulebook` is its only source, including the course labels; the SPA course dropdowns read from it.

`GET /api/wa1500/search?q=` (admin only) looks up the WA1500 register at the fixed host `https://wa1500.org` (`internal/wa1500`: UTF-8 form POST to `class.php`, response decoded by its declared charset, 10 s timeout, 2 MiB size cap, `LAST,  First` names split into last and first name) and returns `{results:[{waid, first_name, last_name, country, club}]}`. Results are cached for five minutes per query and searches are limited to ten per minute (`429`); an unreachable or unusable upstream returns `503` so the client can fall back to manual entry.

`POST /api/shooters/import` (admin only) stores a WA1500 hit locally (ADR 0014). The body is the shooter fields (`waid` required, `first_name`, `last_name`, `country` and `club`) plus optional `update_shooter_id` or `create_new` (mutually exclusive, otherwise `422`). A shooter with the same WAID is updated silently and the call returns `200 {id, action:"updated"}`. Otherwise shooters with the same first and last name (case-insensitive) cause `409 {error:"name_conflict", candidates:[shooter...]}`; the client resends with `update_shooter_id` (must be one of those candidates, else `422`), which updates it and attaches the WAID, or with `create_new: true`. A match with an archived shooter, by WAID or as the chosen `update_shooter_id`, answers `409 {error:"shooter_archived", shooter}` and changes nothing; import never changes archive state. The `Wa1500Import` component then shows "matched an archived shooter" with an Unarchive button that unarchives the shooter and repeats the import. With no match the shooter is inserted and the call returns `201 {id, action:"created"}`. The Shooters page (`/admin/shooters`) has a Search shooters box (server-side `q`) and an Import from WA1500 panel, the shared `Wa1500Import` component: a search box with an explicit Search button, a hit list where each hit has an Import button, a Name already exists dialog on `409` (update one candidate or Create new shooter), and a manual entry form (Enter manually, shown automatically when the lookup answers 503) that creates the shooter with `POST /api/shooters`. Both manual shooter forms (this one and the Shooters page form) list First name before Last name and show the Normalized name while typing (`web/src/lib/names.ts` mirrors the Go rule; casing applies on every keystroke, whitespace is trimmed and collapsed on blur and submit). The component reports the saved shooter through an `onsaved` callback so the Entries picker can reuse it.

## Backend

Go, chi, SQLite-format storage via Turso Database and `turso.tech/database/tursogo` (`CGO_ENABLED=0`, native library loaded at runtime; see ADR 0005), embedded ordered migrations, strict handler → service → repository layering, `excelize` for xlsx, `certmagic` for ACME. Passwords hashed with argon2id (random salt per user, PHC string, m=19456 KiB, t=2, p=1, rehashed at login when weaker, constant-time comparison, dummy verification for unknown usernames; login answers wrong password and unknown username identically; failed logins are limited per IP and delayed per username, never hard-locked); session cookie `HttpOnly`, `SameSite=Lax`, `Secure` when `BASE_URL` is https.

## Configuration (environment only)

`ADMIN_USERNAME` and `ADMIN_PASSWORD` (16-128 chars), both required only while there are no users, `DB_PATH`, `LISTEN_ADDR`, `BASE_URL`, `TRUSTED_PROXY`, `TLS_CERT_FILE`, `TLS_KEY_FILE`, `ACME_DOMAIN`, `ACME_EMAIL`, `TURSO_GO_CACHE_DIR` (writable path for the extracted native library), `REPLICATION_URL` (empty disables Replication), `REPLICATION_INTERVAL` (default 60s).

## Replication

Optional and off by default. When `REPLICATION_URL` is set, the primary opens its database through the tursogo sync API and pushes to a self-hosted `tursodb --sync-server` on another host, every `REPLICATION_INTERVAL` and when a match finishes. Push-only: the replica is never merged back. Failures are logged and retried and never block scoring. The sync server has no authentication, so it must only be reachable over a private network; across the public internet use snapshot files instead. Restore is copying the replica's database file to a new primary. See ADR 0005.

TLS modes: plain HTTP (default, behind a proxy); static certificate; ACME via certmagic with certificates stored in the data volume.

## Score log

Whenever a stage changes status (a device or user lock, an accept, a dispute, an unlock, or an admin overwrite of ring counts), the server writes one JSON `info` line to stdout with `msg` and `event` `stage_status` and the stage's new `status` (`open`, `awaiting_acceptance` or `accepted`). A device lock gives `awaiting_acceptance`; a user lock or accept gives `accepted`; a dispute gives `open` with `disputed_at` set and the lock fields empty; an unlock gives `open` with the ring counts kept and `locked_by`, `scorer_name`, `locked_at` and the accepted fields empty. A user's overwrite of ring counts on a stage awaiting acceptance or accepted ends `accepted` and takes it over: the line has `locked_by` and `scorer_name` set to the user's username, and the database records the same, so the original device lock is no longer visible; `locked_at` keeps the original lock time. Fields: `schema_version` (3), `event`, `status`, `emitted_at` (UTC, fixed-width millisecond precision such as `2026-10-19T16:45:14.123Z`), `seq` (integer that strictly increases for every line within a server process, assigned under a mutex so it matches write order), `competition` {`id`, `name`}, `match` {`id`, `name`, `date`, `course_of_fire` {`key`, `discipline`, `total_shots`}}, `entry` {`id`, `lane`, `category`, `shooter` {`waid`, `first_name`, `last_name`, `club`}}, `stage` {`number`, `expected_shots`}, `ring_counts` (X, 10, 9, 8, 7, 0, miss), `locked_by` (lane number for a device lock, username for a user lock), `scorer_name` (the username for a user lock), `locked_at`, `accepted_by`, `accepted_at`, `disputed_at`. The line is written after the database write succeeds; a log failure never fails the transition. Editing a match, an entry or a shooter re-emits `stage_status` for every affected stage that is not open (a shooter edit covers all of that shooter's entries across matches) as currently recorded and with a new `emitted_at` and `seq`; open stages emit nothing. Replay: the last line per match, entry and stage by (`emitted_at`, `seq`) wins; `seq` restarts at 1 after a server restart, which is safe because `emitted_at` is compared first, and a final `open` line means the stage is open with its ring counts. Entries with no status change are not recoverable, and lines contain personal data. The `restore` subcommand (`matchmark restore [file]`, stdin when no file is given; no `ADMIN_USERNAME` or `ADMIN_PASSWORD` needed) parses the log, skips non-score and malformed lines (including an unknown course key or status, a `locked_by` that is neither a positive lane number nor a non-empty username on a locked stage, or an `emitted_at` not in the fixed-width layout) with a count, rejects any other `schema_version` (including version 2, written before Competition and Match were split, and the retired version 1 `stage_locked` and `stage_unlocked` lines), applies the replay rule with context taken from the latest line, and prints a summary of the matches, entries and stages. Without `--apply` it is a dry run and writes nothing. With `--apply` it opens the database from the server configuration (`DB_PATH`), runs migrations and recreates each match (status `finished` when every stage is accepted, otherwise `active`), its shooters (matched by WAID, else by name and club), entries and stages with ring counts, status, `scorer_lane` (NULL for a user lock), `scorer_name`, `locked_at` and the accepted fields, keeping the original match and entry ids. It refuses a database that already contains matches or shooters and changes nothing; all matches are written in one transaction, so a failure changes nothing; flags may follow the file path; `--merge` instead applies only data whose ids match or are new, lists conflicts (a differing match, entry, or non-open stage counts, status, `locked_by`, `scorer_name` or `locked_at`) and never overwrites them. It is idempotent by ids and leaves stages that are not open untouched. Country is not in the log, so restored shooters get an empty country. Unscored entries, devices and pairings are not restored and the command says so, including that devices must be re-paired before scoring continues; awaiting-acceptance stages are restored intact, a dispute-reopened stage is restored open with its hits, and the current stage is the lowest stage not accepted by every restored lane. See ADRs 0007 and 0013.

## Audit log

Every mutation, login, failed login, failed password change, report download, backup download and `reset-password` run is written to the `audit_log` table and, after the database write succeeds, to stdout as a JSON `info` line with `msg` `audit`. The service layer writes both, so every entry point is covered; a write failure is logged and never fails the request. Fields: `time` (UTC), `user_id` (absent for devices and failed logins), `username` (the username at the time of the event; the attempted username for a failed login; `device` for a paired device), `action`, `target`, `details`, `ip` (the client IP, honouring `TRUSTED_PROXY`). Actions: `competition.create|update|delete`, `match.create|update|status|visibility|delete`, `shooter.create|update|archive|unarchive|delete|merge`, `entry.add|update|withdraw|delete`, `stage.set_counts|lock|accept|dispute|unlock`, `match.next_stage|accept_all`, `club.update|logo.set|logo.delete`, `device.pair|revoke`, `user.create|deactivate|reactivate|reset_password|set_role|set_backup_permission|change_password|change_password_failed`, `login`, `login_failed` (details `throttled` when the per-IP limit answered), `report.download` (details `xlsx`, `csv`, `pdf` or `zip <format>`) and `backup.download`. Counts entered and locks made by a paired device have actor `device` and details `lane <n> match <id>`; `user.reset_password` from the `matchmark reset-password` command has actor `cli`. A failed password change (wrong current password) is recorded as `user.change_password_failed`. Only successful changes are recorded. Targets look like `match:3`, `match:3/entry:7/stage:1` or `user:2`. Entries are kept forever; database triggers reject updates and deletes and there is no write or delete endpoint. `GET /api/audit-log` (admin only; users get 403) returns `{entries, total, page, page_size}` newest first, filtered by `user` (case-insensitive username), `action` (exact), `from` and `to` (`YYYY-MM-DD`, UTC, inclusive), with `page` and `page_size` (default 50, maximum 200); invalid parameters answer 422. The admin UI shows it at `/admin/audit` (menu entry visible to admins only). Seeding the first admin is not audited. See ADR 0011.
